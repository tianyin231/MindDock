# MindDock：随身、安全、分门别类的第二大脑

> **设计与实施方案 · v2.2**
> **编制日期：2026-10-23，2026-10-24 更新（部署、账号体系、面板设置）**
> **仓库：https://github.com/tianyin231/MindDock**
> **实施环境：海外 Linux 云服务器（带宽尚可）；夸克网盘会员；OpenAI 兼容 AI 接口；QQ 开放平台官方机器人（新建专用）；主力手机为安卓**
> **前身：v1《Personal Hub 部署与扩展实施方案》（[archive/Personal_Hub_Deployment_Guide.md](archive/Personal_Hub_Deployment_Guide.md)），其中的最小权限、加密备份、恢复演练原则继续沿用**

**一句话目标**：在 QQ 里像给自己发消息一样发送文字、网址、图片、视频、文件和密钥；MindDock 自动去重、整理，把每条消息归入笔记、收藏、待办、提醒、密钥、文件等分区，到点通过 QQ 主动提醒；原件归档到夸克网盘；在网页面板上实时看到归类过程并统一管理，密钥需要登录二次验证加二级密码才能查看。

## 1. 结论与相对 v1 的变化

| 项目 | v1 | v2.1 | 原因 |
| --- | --- | --- | --- |
| 记录入口 | Memos 网页；分享菜单、快捷键、离线队列放到第二阶段自研 | QQ 官方机器人私聊（新建专用机器人） | 分享菜单、断网重发、送达状态由 QQ 客户端现成提供，"随手发"在第一版就成立 |
| 核心系统 | Memos 0.31 | 自研轻量服务（Python + SQLite） | Memos 附件不支持网盘、没有密钥库，且 0.30 / 0.31 / 26.10 连续出现破坏性接口变更 |
| 分类 | 标签 | 七个分区，各有专属字段和视图 | 收藏、待办、提醒、密钥需要不同的展示和操作 |
| 面板 | Memos 网页 | React 单页应用，实时展示归类动画 | 要求界面精致、各分区一目了然 |
| 提醒 | 无 | 优先被动回复，其次 QQ 主动消息，邮件兜底 | 官方机器人主动消息额度很少（见第 7 节），能回复时优先回复 |
| 原件存储 | Cloudflare R2 | 夸克网盘（经 OpenList）；R2 只放数据库备份，并作为备用后端 | 空间与成本；已有夸克会员 |
| 密钥 | 不进系统，仅 KeePassXC | 机器人可直接收；公钥加密入库，二级密码在浏览器内解密 | 接受经 QQ 传输的风险，换取收集方便 |
| 远程访问 | Tailscale | 域名 + HTTPS + 密码 + TOTP；无域名时退回 Tailscale | 海外服务器无需备案；手机不必常驻 VPN |
| AI | 第三阶段 | 第一版就做归类、标题、摘要、标签、时间解析；向量检索放 M2 | 整理是核心价值，且不依赖向量库 |

**第一版不做**：多用户、公开分享、手机相册全量备份、音视频转写、向量数据库、自研客户端。

## 2. 系统架构

```text
手机 / 电脑：系统分享菜单 → QQ 私聊 → MindDock 机器人（QQ 官方）
                                   │ WebSocket（服务器主动连出，不开入站端口）
                                   ▼
┌──────────────────── 海外云服务器（Docker Compose）────────────────────┐
│                                                                      │
│  bot      收消息 → ①密钥判定 → ②落本地暂存 + SQLite → ③立即回执 ✅     │
│           到点提醒、异常告警：QQ 主动消息（失败时改发邮件）               │
│  worker   后台任务：抓网页 / AI 归类整理 / 缩略图 / 上传夸克 / 备份 / 提醒调度 │
│  panel    JSON 接口 + SSE 实时推送 + 托管前端页面                        │
│  openlist 夸克 cookie 驱动 → WebDAV（仅容器内网）                      │
│  caddy    面板 HTTPS 入口（宝塔 nginx 在 443 按域名分流给它）         │
│                                                                      │
│  data/minddock.db（SQLite）  data/staging/  data/thumbs/  data/vault/ │
└──────────────────────────────────────────────────────────────────────┘
          │ 原件                                 │ 每日加密备份
          ▼                                      ▼
   夸克网盘（原件主仓库）                  夸克 + Cloudflare R2（两份）
```

| 服务 | 职责 | 对外暴露 |
| --- | --- | --- |
| `bot` | 连接 QQ 网关，解析消息，去重，密钥判定，下载附件，回执；发送提醒和告警 | 无（只出站） |
| `worker` | 执行任务队列中的所有后台任务，调度到期提醒 | 无 |
| `panel` | JSON 接口、SSE 实时事件、面板上传、托管前端构建产物 | 仅经 `caddy` |
| `openlist` | 把夸克挂载为 WebDAV | 无；管理界面经 SSH 隧道访问 |
| `caddy` | HTTPS 与证书自动续期 | 仅本机端口；宝塔 nginx 在 443 按 SNI 转来本域名的连接（不解密，PROXY protocol 带真实 IP），80 端口整体反向代理给它 |

`bot`、`worker`、`panel` 使用同一份代码、同一个镜像，只是启动命令不同；共享一个 SQLite 数据库（WAL 模式，设置 `busy_timeout`）。三个进程之间通过数据库表传递事件（例如 `events` 表），`panel` 读取后经 SSE 推给浏览器。

## 3. 七个分区

| 分区 | 标识 | 内容 | 专属字段与视图 |
| --- | --- | --- | --- |
| 处理中 | `inbox` | 刚收到、AI 尚未归类，或归类失败的条目 | 识别中动画；失败原因与重试 |
| 笔记 | `note` | 想法、随手记、长文字 | 按日期分组的时间线 |
| 收藏 | `bookmark` | 网址、文章、值得留存的图文 | 网页卡片：封面、标题、站点、摘要 |
| 待办 | `todo` | 需要去做的事 | 勾选完成、截止时间（今天 / 明天 / 已逾期） |
| 提醒 | `reminder` | 带时间的提醒 | 提醒时间、重复规则、送达状态 |
| 密钥 | `secret` | API Key、密码、私钥等 | 默认锁定；二级密码解锁后查看、复制 |
| 文件 | `file` | 图片、视频、文档等以附件为主的条目 | 图片墙、文件列表、上传状态 |

- 密钥在收件阶段就被分流到独立的 `secrets` 表，从不进入 `items` 和 AI；其余分区由 AI 归类，用户可以手动改分区，手动结果优先。
- 一条消息只属于一个分区；同时含文字和附件时，由 AI 判断主要意图（例如"这张图明天提醒我看"归入提醒，图片作为附件）。

## 4. 消息处理流程

### 4.1 收消息（bot）

1. 收到私聊消息事件。**发送者 openid 不在白名单内直接丢弃**，只在日志中记录 openid，便于首次配置。
2. 以 QQ 消息 ID 去重；已处理过的消息只回复"已存在 #编号"。
3. **密钥判定**（见第 5 节）在内存中完成。判定为密钥的内容不写入暂存目录、普通数据表和日志。
4. 普通消息写入 `items`（分区为 `inbox`）；附件立即流式下载到 `data/staging/`，边下载边计算 SHA-256，写入 `files`。QQ 附件链接有时效，下载失败时在几分钟内短间隔重试。
5. 为条目入队后台任务：`fetch_link`（含网址时）→ `organize` → `thumbnail` → `upload`。
6. 回复回执，例如 `✅ #A3F9 已收：文字 1、图片 2`。AI 归类完成后，提醒类条目追加一条确认，例如 `⏰ #A3F9 已设提醒：10/24（周五）15:00`。
7. 写入 `events`，面板实时显示"收到 → 归类"的动画。

消息约定：

| 写法 | 含义 |
| --- | --- |
| 直接发送 | 由 AI 归类 |
| `明天下午三点提醒我交报告` 等含时间的说法 | AI 识别为提醒并解析时间 |
| `#key 名称`，换行后写内容，或附图片/文件 | 存入密钥库 |
| `#noai` | 本条不送 AI，留在"处理中"等待手动归类 |
| `#任意词` | 用户标签，与 AI 标签分开保存 |
| `/s 关键词` | 搜索，回复前 5 条的编号和标题 |
| `/todo` | 列出未完成待办 |
| `/状态` | 待上传数量、失败任务、存储健康状态 |

### 4.2 后台任务（worker）

- 由 `jobs` 表驱动，状态流转：`queued → running → done`，失败进入 `failed` 并按计划重试，超过上限进入 `dead`，在面板可手动重试。
- 重试间隔：1 分钟、5 分钟、30 分钟、2 小时、6 小时，之后每 12 小时一次。
- 同一条目的同类任务只保留一个活动任务（幂等）。
- worker 启动时把超时未结束的 `running` 任务放回队列。

## 5. 密钥库

### 5.1 识别

识别发生在任何持久化之前：

1. **显式**：消息以 `#key` 开头。这是最可靠的方式，建议养成习惯。
2. **自动**（兜底）：命中以下任一规则即按密钥处理，并在回执中说明"已按密钥保存，如误判可在面板移出"：
   - 私钥文件头 `-----BEGIN ... PRIVATE KEY-----`；
   - 常见令牌格式：`sk-…`、`ghp_…` / `github_pat_…`、`AKIA…`、`xoxb-…` / `xoxp-…` 等；
   - `password` / `token` / `secret` / `api_key` / `密码` / `密钥` 后跟 `:`、`=` 或 `：` 以及 8 位以上的值；
   - 长度不小于 32、字符种类混合、熵值高且不是网址的单个字符串。

图片中的密钥无法事先识别，截图类密钥必须加 `#key`。

### 5.2 加密方案

使用 libsodium（服务器端 PyNaCl，浏览器端 libsodium-wrappers-sumo，含 Argon2id）。

| 环节 | 做法 |
| --- | --- |
| 初始化（浏览器内） | 生成 X25519 密钥对；用 Argon2id(二级密码, 随机盐) 派生的密钥加密私钥；另生成一个只显示一次的恢复码，同样包裹一份私钥；只把公钥、两份包裹后的私钥、盐和参数上传到服务器 |
| 入库（服务器） | 用公钥 sealed box 加密，数据库只存密文。加密不需要二级密码，所以机器人能自动保存 |
| 查看（浏览器内） | 面板已登录（密码 + TOTP）→ 输入二级密码 → 浏览器解开私钥并解密；空闲 5 分钟或页面切到后台即自动锁定 |
| 修改二级密码 | 浏览器重新包裹私钥即可，已存密钥不用重新加密；提交前须解开服务器用公钥加密的随机挑战，证明持有私钥，防止会话被盗后覆盖包裹 |
| 忘记二级密码 | 用恢复码解开私钥，设置新二级密码并换发新的恢复码，旧恢复码作废 |
| 面板新增 | 浏览器用公钥加密后提交，服务器只收到密文 |

- Argon2id 参数按手机浏览器约 1 秒调优，起步 64 MiB、3 轮。
- 密钥类图片和文件同样整体加密，单个上限先定 20 MB，密文存于 `data/vault/`，随数据库一起进入加密备份。
- "移出密钥库"（误判时）需要先在浏览器内解密，再作为普通条目提交；原密钥进回收站。
- 名称是明文（显式 `#key 名称`，自动识别时取识别原因），内容才加密；一条消息的文字和每个附件分别存为一条密钥。
- 二级密码输入框不让浏览器保存：支持 `-webkit-text-security` 的浏览器用普通文本框加遮罩，其余用密码框并关闭自动填充。

### 5.3 能防什么、不能防什么

| 情形 | 结果 |
| --- | --- |
| 数据库或备份泄露 | 只有密文和 Argon2id 包裹的私钥，安全性取决于二级密码强度 |
| 面板登录密码泄露 | 还需要 TOTP；登录后不输二级密码仍看不到明文 |
| 服务器被完全控制 | 攻击者可以篡改面板前端截获二级密码，属于残余风险 |
| QQ / 腾讯侧 | 明文经过腾讯服务器并留在聊天记录中。回执提醒 2 分钟内撤回，可减少多端残留，但不保证服务器端删除 |

**不经过本系统的凭据**：服务器 root SSH 私钥、二级密码与恢复码、备份解密私钥、主邮箱恢复码。这几样放 KeePassXC 并离线备份。

**日志纪律**：全系统日志只记录条目编号、类型和大小，任何消息内容都不写入日志。

## 6. AI 整理

### 6.1 输入准备

| 类型 | 处理 |
| --- | --- |
| 文字 | 原文，连同当前时间与时区（用于解析"明天下午三点"） |
| 网址 | 抓取网页（超时 15 秒、上限 2 MB），用 trafilatura 提取正文，截断到约 8000 字 |
| 图片 | 配置了视觉模型时，缩放到长边 1568 像素送入，输出识别文字和画面描述 |
| PDF | 本地提取前若干页文字 |
| 视频 / 语音 / 其他文件 | 第一版只记录元数据（时长、尺寸、文件名） |

### 6.2 输出

固定 JSON 结构，用 pydantic 校验：

```json
{
  "partition": "note | bookmark | todo | reminder | file",
  "title": "不超过 30 字",
  "summary": "不超过 200 字",
  "tags": ["最多 5 个"],
  "due_at": "待办截止时间，ISO 8601，可空",
  "remind_at": "提醒时间，ISO 8601，可空",
  "repeat": "none | daily | weekly | monthly",
  "ocr_text": "图片中的文字（仅图片）"
}
```

- 提示词中带上已有的高频标签，鼓励复用，避免同义标签泛滥。
- 优先使用 `response_format` 的 JSON Schema 模式；接口不支持时降级为 JSON 模式加校验重试。
- `partition` 为 `reminder` 但 `remind_at` 缺失或已过去时，降级为待办，并在回执中说明。
- 结果写入 `derived` 表并记录模型名与提示词版本，**原文从不修改**。
- 面板上手动设置的分区、标题、标签优先于 AI 结果，重新整理不会覆盖手动修改。
- AI 接口故障不影响收件：条目停留在"处理中"，任务自动重试，也可在面板手动归类。

### 6.3 配置

`AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL_TEXT`、`AI_MODEL_VISION`（可空）、`AI_MODEL_EMBED`（M2 起使用）；时区 `TZ`，默认 `Asia/Shanghai`。

## 7. 提醒

- **调度**：worker 每 30 秒检查一次到期提醒（`status = scheduled` 且 `remind_at` 或 `snooze_at` 已到），离下一条不足 30 秒时按它的时间醒来；到点的提醒进入任务队列，由 `remind` 任务送达。服务重启后补发错过的提醒，并在消息中标注"（延迟送达）"。
- **QQ 平台限制**（2026-10 核实）：官方机器人自 2025-04-21 起不再保证主动消息（文档仍写"单聊每月 4 条"，实测可发但额度很少）；被动回复在收到消息后 60 分钟内有效，同一消息最多 5 次，`msg_seq` 不能重复。
- **送达顺序**（`notify.py`）：
  1. 被动回复：主人最近 55 分钟内发来、回复次数未用完的消息（`qq_inbound` 表统一分配 `msg_seq`，bot 与 worker 共用）；
  2. QQ 主动消息；
  3. 邮件（在面板配置后启用），正文附面板链接。
  全部失败时记录原因并按任务退避重试；超过预定时间 3 小时仍发不出去，单次提醒标记为失败，重复提醒跳过本次。
- **重复提醒**：每天 / 每周 / 每月，按锚点时间 `anchor_at` 在本地时区推算下一次，月末日期不会漂移（1 月 31 日 → 2 月 28 日 → 3 月 31 日）；送达后 `remind_at` 前移，状态保持 `scheduled`。
- **QQ 内操作**：`/done` 完成刚收到的提醒（或 `/done #A3F9` 指定条目，待办同样适用）；`/later 30m`（`2h`、`1d`，可带编号）稍后再提醒；`/提醒` 列出接下来的提醒。重复提醒的 `/later` 只记在 `snooze_at`，不打乱原有节奏。
- **面板操作**：完成、稍后（10 分钟到明天）、改时间与重复规则、取消；移出"提醒"分区时自动取消未发送的提醒。设置页可发送一条测试消息检查主动消息是否可用。
- 渠道做成可插拔接口，日后可加 ntfy 等推送方式。

## 8. 存储层

### 8.1 接口与后端

统一接口：`put` / `stat` / `open` / `delete`。实现三个后端：

| 后端 | 用途 |
| --- | --- |
| `quark`（OpenList WebDAV） | 原件主仓库 |
| `r2`（S3 接口） | 数据库备份；夸克失效时的备用主仓库 |
| `local` | 开发与测试 |

每个文件记录自己所在的后端，所以中途切换主后端不影响旧文件；日后可按 SHA-256 在后端之间迁移。

### 8.2 夸克（经 OpenList）

- OpenList 用 cookie 挂载夸克，只在容器内网提供 WebDAV；管理界面不对外，需要时通过 SSH 隧道访问。
- **已知限制**：OpenList 的夸克驱动基于逆向接口，官方表明不再维护；夸克传输强制经服务器中转；cookie 会过期。因此夸克被设计成"随时可替换"的一环，而不是系统核心。
- **为什么用 cookie**：夸克没有对个人开发者开放网盘接口（open.quark.cn 是小程序平台；带 OAuth 的网盘接口只供夸克自家和合作产品使用）。OpenList 的"夸克 TV"驱动用扫码令牌，但不支持上传。
- **cookie 的寿命**（2026-10 实测）：真正的登录凭据是 `__pus`；`__puus` 每次请求都会换新、24 小时过期，缺了夸克也会按 `__pus` 重新签发，所以闲置几天不影响。cookie 失效主要因为在浏览器里退出登录、改密码或被踢下线，因此建议在无痕窗口登录后复制，复制完直接关窗口。保存时校验必须带 `__pus`。
- 远端路径：`/MindDock/originals/2026/10/20261023-153012_A3F9_原文件名.jpg`。明文可读，系统停用时也能在夸克 App 中直接找到。
- 上传流程：流式 PUT → 查询远端大小并比对 → 标记 `uploaded`。远端已有同样大小的文件（上次传完未记录）则直接标记；同名文件会被覆盖，失败重传安全。
- 上传任务由单独的消费者执行，不占用 AI 整理和提醒；附件下载完成后自动排队，例行维护补排遗漏的文件。
- 连续 3 次上传失败即把存储标记为异常：通过 QQ 告警一次（QQ 发不出时改发邮件），面板顶部显示横幅；在面板更新 cookie 后，失败的文件自动重新排队补传。夸克返回 `require login`（cookie 失效）是确定的，第一次就告警。
- 登录状态检查：超过 6 小时没和夸克交互（没有成功上传），例行维护就列一次夸克根目录确认 cookie 仍有效；失败后每小时再查。这样几天不发文件，cookie 失效也能及时发现。

### 8.3 本地暂存与缩略图

- 原件在**上传确认前绝不删除**；上传成功后默认保留 7 天（`MINDDOCK_STAGING_KEEP_DAYS`），磁盘可用空间低于 20% 时提前清理最旧的已上传原件。
- 缩略图永久保存在本地：图片转为最宽 480 像素的 WebP（已实现）；视频封面（ffmpeg）与 PDF 首页暂未实现，用图标占位。面板浏览只读缩略图，不依赖网盘速度。
- 面板下载原件：本地还在就直接返回；否则经 OpenList 从夸克流式取回（需已登录，支持 Range）。

### 8.4 删除

面板删除先进回收站，保留 30 天，到期后再删除远端文件。

### 9.3 登录与安全

- **首次初始化**：面板开放在公网，首次打开需要输入只打印在服务器日志里的一次性初始化码，然后创建唯一账号并绑定验证器（TOTP）。
- **日常登录**：用户名 + 密码（Argon2id 哈希），使用标准登录表单，浏览器可保存并自动填充；在新浏览器上额外输入验证码，可勾选"信任此设备 30 天"，期间只需密码。TOTP 种子用主密钥加密后存库，同一验证码只能用一次。
- **密钥库二级密码不允许浏览器保存**，每次手动输入。
- 服务端会话表与受信任设备表只存令牌哈希；Cookie 设置 HttpOnly、Secure、SameSite=Strict；会话 30 天。
- 修改类请求必须带 `X-MindDock` 请求头，配合 SameSite 防 CSRF。
- 登录失败限速：同一 IP 每分钟 5 次，连续 10 次失败锁定 15 分钟。
- 内容安全策略（CSP）只允许加载本站脚本；所有前端依赖打包进构建产物，不使用 CDN。
- 登录、密钥库访问、删除写入审计日志。

### 9.4 中文搜索

SQLite FTS5 使用 `trigram` 分词器，支持 3 字及以上的任意子串检索；1–2 字的查询回退到 `LIKE` 扫描，个人数据量下足够快。语义搜索在 M2 加入。

## 13. 备份与恢复

| 内容 | 方式 | 去向 |
| --- | --- | --- |
| 数据库 | 每日 03:15 执行 `sqlite3 .backup`，再做 `PRAGMA integrity_check` | 与下两项一起打包 |

| 配置 | `.env`、`compose.yaml`、OpenList 配置 | 同上 |
| 备份包 | 用 age 公钥加密 | 本地保留 7 份；夸克与 R2 各保留 30 份日备 + 12 份月备 |

**恢复演练**每月一次：在临时目录解密备份 → 完整性检查 → 只读启动面板 → 随机抽 5 条打开原件并核对 SHA-256。

## 14. 风险与兜底

| 风险 | 影响 | 兜底 |
| --- | --- | --- |
| 夸克驱动为逆向接口且不再维护；cookie 失效 | 原件上传中断 | 本地排队不丢；QQ 主动告警与面板横幅；改配置即可切换到 R2 |
| QQ 主动消息额度或限频 | 提醒发不出 | 自动改发邮件；面板显示送达状态 |
| QQ 私聊附件大小上限、平台规则变化 | 大文件进不来 | 面板网页上传；入口模块独立，可增加其他入口 |
| QQ 附件链接过期 | 附件下载失败 | 收到即下载，短间隔重试 |
| AI 接口故障或输出不合规 | 条目停在"处理中" | 任务重试；面板手动归类 |
| AI 时间解析错误 | 提醒时间不对 | 回执中明确回显解析出的时间，可在面板或 QQ 中修改 |
| 服务器磁盘写满 | 无法收件 | 暂存清理策略；磁盘阈值告警 |
| 二级密码遗忘 | 密钥无法解密 | 恢复码（离线保存） |
| 腾讯侧留存密钥明文 | 凭据泄露面扩大 | 回执提醒撤回；最高等级凭据不走 QQ |
| 夸克内容审核或账号异常 | 原件不可访问 | 数据库备份在 R2 另有一份；重要原件可选双存 |

## 15. 实施计划与验收

### 第 1 步：项目骨架

### 第 3 步：验证（约半天，可与第 2 步并行）

| 编号 | 验证内容 | 通过标准 | 不通过时 |

| V1 | 新建的 QQ 机器人从海外服务器接收文字、图片、文件、视频、语音；记录附件大小上限、链接有效期、被动回复窗口、主动消息额度、openid 是否稳定 | 图片和 20 MB 以上的文件能收到；主动消息可用 | 大文件改走面板上传；提醒以邮件为主 |

| V3 | AI 接口的 JSON Schema 输出、图片输入、embeddings；中文时间表达解析准确率 | JSON 输出可用，时间解析正确 | 降级为 JSON 模式；时间解析加规则兜底 |

### M0：基础闭环

交付：`bot`、`worker`、`panel`、`openlist`、`caddy`；收件、去重、密钥库、AI 归类、提醒、缩略图、上传夸克、面板浏览与搜索。

验收：

- [ ] QQ 分享文字、链接、图片、文件、视频，10 秒内收到回执；
- [ ] 面板实时显示新消息，并以动画归入正确分区；
- [ ] 同一条消息重复投递不产生重复条目；

## 16. 开工前需要准备

| 项目 | 说明 |
| --- | --- |
| QQ 开放平台 | 新建专用机器人，获取 AppID、AppSecret，开启单聊消息，把自己的 QQ 加入沙箱 |
| 夸克 cookie | 在无痕窗口登录夸克网页版，按 F12 复制 drive-pc.quark.cn 请求的 Cookie，复制后直接关窗口（不要退出登录）；保存在 KeePassXC |
| AI 接口 | 地址、key、文字模型名；是否有视觉模型；是否支持 embeddings |
| 邮件兜底 | 一个发件邮箱的 SMTP 信息，收件地址为你的 QQ 邮箱 |

| 服务器信息 | 系统版本、CPU / 内存、剩余磁盘、是否已安装 Docker |
